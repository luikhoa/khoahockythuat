# Repository Guidelines

## Project Structure & Module Organization

CyberShield is a Chrome/Edge extension that classifies Vietnamese text with a PhoBERT model exported to ONNX and run entirely inside the extension (offscreen document + Web Worker + ONNX Runtime Web, WebGPU with a WASM fallback). No backend is contacted at runtime. Keep extension TypeScript under `extension/src/`: `content/` scans and annotates page text, `popup/` renders the extension UI and model/status, `inference/` owns the tokenizer/ONNX runtime and worker protocol, `offscreen/` hosts the long-lived inference worker, and `lib/` contains the internal message client, shared type contracts, stats, and link checks. `extension/build.js` validates and copies the exported model plus ONNX Runtime Web's WASM assets, then emits loadable files to the ignored `extension/dist/` directory; `manifest.json` and `content.css` remain at the extension root. `backend/` is training/export tooling only — `export_onnx.py` produces the browser artifact, `verify_onnx.py` gates Python↔ONNX parity, `predictor.py`/`model.py` are the Python oracle; `server.py`/`storage.py` (FastAPI/SQLite) are not started as part of using the extension. Browser fixtures are in `demo/`. See `README.md` and `docs/LOCAL_MODEL_WORKFLOW.md` for the full architecture and the export→parity→build→E2E pipeline.

## Build, Test, and Development Commands

Extension (no backend needed to use it): from `extension/`, run `npm ci`, then `npm run verify` (typecheck + Vitest + build). `extension/model/` must exist first — export it with `python -m backend.export_onnx --offline --model-version <name> --output extension/model` from the repo root (`.venv` with `backend/requirements.txt` installed), or use `CS_SKIP_MODEL=1 npm run build` for a model-less dev build. `npx playwright install chromium && npm run test:e2e` runs the offline Chromium smoke test (no FastAPI, network blocked outside the local fixture). To exercise the standalone demo after building, run `python3 -m http.server 8080` from the repository root and open `/demo/demo.html` or `/demo/feed_demo.html`.

Model tooling (only needed to re-export/verify a model, not to use the extension): from the repo root with `.venv` active, `python -m backend.export_onnx ...` then `python -m backend.verify_onnx --model extension/model --output tests/results/onnx_parity_summary.json` — the parity gate must pass (≥99% label agreement, ≤0.01 F1 loss) before shipping a new artifact. `python -m pytest tests/unit -q` runs export/parity/predictor/server tests.

## Coding Style & Naming Conventions

Use four spaces for Python and two spaces for TypeScript, matching existing files. Keep TypeScript strict: do not introduce unused locals, implicit return paths, or untyped message payloads. Use `camelCase` for TypeScript values and functions, `PascalCase` for interfaces/classes, and `snake_case` for Python functions, variables, and modules. Preserve the internal message contract between `extension/src/lib/types.ts` (`ExtensionMessage`/`ExtensionResponse`) and the service worker/offscreen host that implements it; update both sides together when it changes. The ONNX artifact contract (two int64 inputs, one float32 `toxic_logit` output, two labels, `maxLength: 128`) is defined by `backend/model_contract.py` and enforced by `extension/build.js` — bump `schemaVersion` and add a runtime migration adapter if it changes. Hand-write CSS in `extension/content.css` or `extension/src/popup/styles.css`; no formatter or linter is configured.

## Testing Guidelines

Extension: Vitest (`npm test`) covers content scanning, stats, background routing, offscreen host, popup, and the inference runtime; Playwright (`npm run test:e2e`) is the offline end-to-end smoke test. Backend/model: `pytest tests/unit` covers export contract validation, parity computation, and the legacy FastAPI routes. Three tests in `tests/unit/test_server_api.py` currently fail by design — they assert the old, since-patched unsafe behavior (unbounded content length, wildcard CORS) of `backend/server.py`, which is not part of the runtime path; treat this as a known, tracked gap rather than something to "fix" by reverting the patches. Add focused tests with any new nontrivial logic, using clear names such as `test_predict_returns_two_probabilities`.
